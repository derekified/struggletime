title: Overview
description: What StruggleTime measures and how weighting works.
---

StruggleTime scores time spent fixing things: break something, dig in, get
it working again. Steady editing and error-fix loops get more credit than
a huge paste you never ran, or long stretches away from the keyboard.

## What gets credit

```
(edit | prompt) -> (test | build | run) -> (follow-up edit | commit)
```

| Pattern | Weight (v0.4.0-alpha) |
|---|---|
| Struggle / fail→fix→pass | 1.00x |
| AI write + dwell + follow-up | 0.85x |
| Human edits, never run | 0.70x |
| Unverified multi-file dump | 0.20x |
| Quiet follow-up after real work | 0.70 → 0 over ~5–12 minutes |
| Idle after the active span | Gradual decay (no hard 240s cliff) |

## How trust works

- **Passive file and git tracking.** The desktop tracker watches saved file
  changes and git activity in your project folder. It does not screenshot
  your screen or read file contents.
- **Salted file IDs.** Paths are mixed with a local salt
  (`sha256(salt:path)`) before anything is sent, so raw paths and source
  stay on your machine.
- **Hash-chained history.** Each sealed time slice stores `prev_hash` of the
  previous entry. Quiet edits to past history show up in review.
- **Shared scoring.** Daemon and server both use `st-core` with the same
  `FORMULA_VERSION`.

## Privacy

`struggletime daemon` is a native binary. Wire payloads are allowlisted
metadata (~25–50 KB) with salted file IDs. See [Privacy](/docs/privacy).
